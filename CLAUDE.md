# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

**Bank AI Firewall** — фаервол между AI-агентом и банком. Две части:

| Каталог | Что это | Язык |
|---|---|---|
| `firewall/` | Веб-приложение: движок правил, журнал, подтверждения человеком. Наш код, Docker. | FastAPI + SQLite, без ORM и без фронтенд-сборки |
| `mcp/` | Форк [icyberdeveloper/tbank-mcp](https://github.com/icyberdeveloper/tbank-mcp) (61 тул к API Т-Банка), доработанный так, чтобы ходить в банк только с разрешения фаервола | Python 3.11+, MCP SDK 1.x |

Агент разговаривает с `mcp/`, `mcp/` перед каждым вызовом спрашивает `firewall/`,
человек управляет политикой в вебморде. Банк ничего об этом не знает.

## Команды

```bash
# Всё в Docker (основной способ)
cp .env.example .env                 # где хранить сессию, uid для прав на неё
docker compose up -d --build         # firewall :8080 + authd :8765
docker compose --profile mcp-http up -d   # плюс MCP по HTTP на :8000
docker compose logs -f firewall authd
docker compose down                  # политика переживает: она в volume firewall-data

# Фаервол локально, без Docker
cd firewall && python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt
TBANK_FW_DB=./data/firewall.db .venv/bin/uvicorn app.main:app --port 8080

# Тесты фаервола (без pytest, каждый файл — самостоятельный скрипт)
cd firewall && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python tests/run_all.py            # все
.venv/bin/python tests/run_all.py policy     # только совпадающие по имени
.venv/bin/python tests/test_policy.py        # один файл напрямую

# MCP
cd mcp && python3.11 -m venv .venv && .venv/bin/pip install -e .
TBANK_FIREWALL=0 .venv/bin/python tests/run_all.py      # см. «Тесты» ниже
.venv/bin/python tests/test_firewall_guard.py           # врезка фаервола

# Вход в банк — демон на хосте, форма в вебморде (http://127.0.0.1:8080/auth)
./bin/tbank-authd                            # запустить один раз, оставить в фоне
.venv/bin/python login_cli.py +7XXXXXXXXXX   # он же из терминала, если так привычнее

# Подключить к агенту
claude mcp add tbank -- /абсолютный/путь/mcp/.venv/bin/python -m src.server
```

`python3.11` — минимум; на 3.9 (системный python3 на macOS) не заводится ни одна
из частей.

## Как устроено решение

Жизненный цикл одного вызова тула:

```
агент → mcp/src/server.py (@mcp.tool)
      → mcp/src/guard.py  wrap()
        → POST /api/v1/authorize     ← ЗДЕСЬ принимается решение
          allow  → вызов уходит в банк → POST /result → ответ проходит через маски
          deny   → в банк НЕ идёт, агент получает текст с причиной
          hitl   → в банк НЕ идёт, агент получает ссылку на подтверждение
```

**Единственная врезка в MCP** — `_traced_tool` в `mcp/src/server.py` (~строка 170).
Все 61 тул регистрируются через неё, поэтому проверка ставится один раз, а не в
каждой функции. Порядок обёрток намеренный: `trace.wrap(guard.wrap(fn))` — guard
внутри, чтобы в `calls.jsonl` попадали и заблокированные вызовы. Обе обёртки
сохраняют `__wrapped__`, на чём держится `tests/test_trace.py`.

**Порядок разбора в `firewall/app/policy.py::evaluate`:**

1. Режим тула (`blocked`/`hidden`) → отказ, дальше не смотрим.
2. Правила по приоритету, **первое совпавшее решает** (ACL, а не сумма весов).
3. Квота сработавшего правила — только если оно разрешает. «До 3000 ₽ три раза в
   сутки молча, дальше спросить» живёт на самом правиле (`quota_*`), а не отдельным
   лимитом: иначе разрешающее правило и его норму надо синхронизировать руками.
4. Если не совпало ни одно правило — политика по умолчанию для `read`/`write`/`money`.
5. Лимиты — **всегда**, даже поверх `allow`, если у правила нет `skip_limits`.

Результаты складываются по строгости: `deny > hitl > allow`.

**Что можно и нельзя унести в Docker.** Фаервол и демон входа — контейнеры.
MCP по **stdio** контейнером быть не может: его запускает сам клиент как дочерний
процесс и говорит с ним через трубу, а держать вторую сторону трубы в контейнере
некому. Поэтому для Claude Desktop / Claude Code он остаётся на хосте и читает ту
же сессию через `TBANK_SESSION`. Клиентам с HTTP-транспортом подходит профиль
`mcp-http` (`TBANK_MCP_TRANSPORT=streamable-http`, `TBANK_MCP_HOST=0.0.0.0`).

Две ловушки контейнеризации, обе стоили отладки:
- **Слушать 127.0.0.1 внутри контейнера бесполезно** — это не петля хоста, и
  опубликованный порт до неё не дотягивается. Отсюда `TBANK_AUTHD_HOST` и
  `TBANK_MCP_HOST`; наружу это ничего не открывает, публикация всё равно на
  `127.0.0.1` хоста.
- **`TBANK_CA_BUNDLE` обязателен в контейнере.** Бандл доверенных корней
  собирается на лету рядом с кодом, а образ принадлежит root при процессе под
  uid пользователя. Без переопределения запись молча не удаётся и отваливаются
  по TLS ВСЕ хосты банка — при живой сессии и рабочей сети.

**Вход в банк** идёт мимо фаервола намеренно. `mcp/src/authd.py` — демон на хосте
(127.0.0.1:8765); вебморда рисует форму на `/auth`, а браузер шлёт введённое
**напрямую в демон**. Поэтому пароль не проходит через контейнер и не попадает
ни в его журнал, ни в контекст модели, а сессия ложится в тот же
`~/.local/share/tbank-mcp/session.json`, который читает MCP. Фаервол о сессии не
знает ничего — он только хранит адрес демона в настройке `authd_url`.

**Ключевые файлы фаервола:**

- `app/catalog.py` — 61 тул: title, kind, категория, и `FACET_MAP` — раскладка
  аргументов тула в факты правил (`to_account` → «получатель», `expected_sum` →
  «сумма»). Единственное место, где живёт эта раскладка.
- `app/facets.py` — извлечение фактов, нормализация телефонов, `signature()`.
- `app/policy.py` — сопоставление, списки, лимиты, окна.
- `app/main.py` — HTTP: API для MCP и страницы для человека.
- `app/seed.py` — стартовая политика (заводится один раз на пустой базе).

## Инварианты, которые легко сломать

- **`kind` тула берётся из `catalog.py`, а не из того, что прислал MCP.** Иначе
  достаточно прислать `kind="read"` на `transfer`. Незнакомый тул считается `money`.
- **Подтверждение одноразовое и привязано к отпечатку вызова** (`facets.signature`:
  тул + аргументы без секретов). Подтвердили 100 ₽ Алёне — пройдёт ровно это.
  Изменение любого аргумента заставляет спрашивать заново.
- **Секреты не попадают в журнал вообще** — `catalog.SECRET_ARGS` (пароль, PIN,
  OTP, платёжный токен) заменяются на длину. Получатель и сумма сохраняются: без
  них журнал не отвечает на вопрос, ради которого заведён.
- **Лимиты считают только `allowed`/`executed`/`unknown`** (`policy.COUNTED_STATUSES`).
  Отклонённый и провалившийся вызов потолок не расходует; неизвестный исход —
  расходует, потому что деньги могли уйти.
- **Квота правила считается по `rule_id`**, а не пересчётом фильтра по истории:
  вопрос звучит как «сколько раз сегодня сработало это правило», и ответ не должен
  меняться от того, что правило потом отредактировали. Операции, подтверждённые
  человеком, идут с `rule_id = NULL` и норму **не расходуют** — квота нормирует
  ровно то, что проходит без подтверждения.
- **Платёжный шлюз требует sessionid уровня CLIENT** (`client._CLIENT_LEVEL_TEMPLATES`).
  Он проверяет SESSIONID, а не Bearer, и окно CLIENT у sessionid ~11 минут против
  ~2 часов у токена. Протухший читается как ANONYMOUS, и шлюз отвечает голым
  `403 Forbidden` или общим «по техническим причинам сервис недоступен» — при
  живой сессии и работающих чтениях, потому что чтения живут на Bearer. Это
  неотличимо от блокировки по антифроду и стоило нескольких дней ложных версий
  (профиль устройства, выдуманные реквизиты). Уровень поднимается в `_call_read`
  и `_call_signed` по списку шаблонов, а не у вызывающих: денежных точек входа
  четыре, и забудут именно в платеже. Обычные чтения лишнего ping не платят.
  Доказано на живом счёте: `payment_commission` (денег не двигает) с одним
  `ensure_fresh` даёт 403, сразу после `ensure_client_session()` — считает.
- **Получатель в НАШЕМ же банке — не маршрут, а тупик** (`client.TBANK_SBP_MEMBER_ID`).
  `get_requisites` зовётся с `withTinkoff=true`, поэтому свой банк попадает в
  кандидаты и часто оказывается дефолтным: получатель — клиент того же банка.
  Авторезолв молча брал его и платил через `p2p-anybank` — внешний рельс СБП
  такого платежа не проводит, а провайдера для внутреннего P2P по номеру здесь
  нет. Шлюз отвечал общим «сервис недоступен», и это читалось как авария банка.
  Теперь `transfer` отказывается и показывает ВСЕ банки получателя, помечая
  свой как «только в приложении». Вычёркивать его нельзя: он у получателя
  есть, и умолчание превращается в неправду — агент начинает уверять, что
  такого банка нет, хотя в приложении перевод туда работает. Не реализован
  он ЗДЕСЬ, а не в банке.
  Доказано живьём: комиссия по тому же конверту считается (она маршрут не
  строит), платёж падает, а тот же перевод с явно выбранным внешним банком
  проходит.
- **Выбор банка — кликом, а не текстом.** `choose_recipient_bank(phone)` делает
  свежий резолв и показывает варианты через **MCP elicitation** (enum-схема →
  клиент рисует кнопки). Клиент без поддержки elicitation получает ссылку на
  страницу `/choice/{id}` в вебморде и тул `firewall_choice(id, wait_sec)` с
  длинным опросом. Свой банк показывается, но кнопка отключена: перевод внутрь
  банка по номеру здесь не реализован.
- **Кандидаты уходят в фаервол при заведении выбора** (`POST /api/v1/choice`), и
  это не про кнопки. Резолв внутри `transfer()` идёт мимо тула
  `transfer_sbp_resolve`, поэтому фаервол про эти реквизиты иначе не знает — и
  сам же отвергает те, что сам предложил выбрать. Ровно это и случилось в живом
  диалоге.
- **`payment_commission` — НЕ валидатор реквизитов.** Она проверяет конверт
  (и именно этим вскрыла требование CLIENT-сессии), но `providerFields` и
  `provider` принимает почти любые: проверено — прошли `transfer-bank`,
  `transfer-deposit-bank`, `c2c-out` и `p2p-anybank` с заведомо неполными полями.
  Поэтому «комиссия посчиталась» НЕ доказывает, что платёж уйдёт по этому
  маршруту. Для маршрута доказательство одно — живой платёж или захват трафика.
- **Агент помнит только БАНК, связку клиент добирает сам.** `bankMemberId` —
  стабильный номер банка в СБП; `pointerLinkId` банк перевыпускает за минуты.
  Поэтому `transfer(bank_member_id=…)` без `pointer_link_id` — основной путь:
  клиент резолвит свежую связку прямо перед платежом. Требование таскать связку
  через переписку гарантировало протухшую при первой же паузе в разговоре, и
  агент упирался в отказ фаервола. Проверка в фаерволе поэтому применяет срок
  годности ТОЛЬКО к связке, а номер банка сверяет по всей истории.
- **`pointerLinkId` протухает.** Это не постоянный идентификатор получателя, а
  связка, которую банк перевыпускает: два резолва одного номера в один банк с
  разницей в минуты дали разные значения. Поэтому фаервол принимает реквизиты
  только из СВЕЖЕГО резолва (`requisites_ttl_sec`, по умолчанию 30 минут), а не
  из любого когда-либо виденного.
- **Платёжные реквизиты проверяются на выдуманность** (`policy.check_requisites`).
  `bankMemberId` и `pointerLinkId` нельзя вывести из номера — их отдаёт только
  `transfer_sbp_resolve`. Модель, у которой не вышло их получить, подставляет
  правдоподобные цифры и идёт платить; так уже было, и банк ответил 403. Фаервол
  запоминает то, что вернул БАНК (`resolved_requisites`, пишется из ответа тула в
  `/result`), и сверяет присланное. Проверка идёт раньше правил и разрешающим
  правилом не отменяется — это не политика владельца, а защита от галлюцинации.
  Пустые реквизиты разрешены: клиент сам сходит в резолв, и это более безопасный путь.
- **Не-JSON ответ сохраняет тело** (`client._unwrap`). Платёжный сервис отвечает
  конвертом с `resultCode`; не-JSON ответ приходит от края (WAF, лимитер) и его
  текст — единственное, что объясняет отказ. Раньше первым шёл `raise_for_status()`
  и наружу уходил голый `HTTPError` с одним URL.
- **Устройство описано ОДИН раз — `client.CAPTURED_DEVICE`.** Оттуда его берут оба
  блоба: `_builtin_fingerprint` (уходит при входе и refresh, им же пользуются
  `authd` и `login_cli`) и `PAY_DEVICE_PROFILE` (уходит в `/v1/pay`). В поставке
  апстрима наборов было два, и они разъехались: вход синтезировал 1170×2532 с
  языком `ru`, платёж посылал захваченные 1260×2736 с `ru-CY`. Одна сессия, один
  deviceId, два телефона в двух странах — чтения работали, потому что не несут
  блока устройства, а `/v1/pay` отвечал 403. Истиной выбран ЗАХВАТ: он снят с
  живого приложения и сверен с captures.xml, а второй блоб был выдуман. `ru-CY` —
  осознанно оставленное свойство того устройства, а не опечатка.
  `TBANK_DEVICE_*` переопределяют оба блоба разом; пинится
  `tests/test_device_and_outcome.py`.
- **HTTP 4xx — это ОТВЕТ, а не неизвестность** (`server._bank_refused`). «Исход
  неизвестен» говорит пользователю, что деньги могли уйти, и включает защиту от
  дублей: следующий такой же платёж требует `force`. Раньше туда попадал живой 403
  от `/v1/pay`, потому что `requests` поднимает `HTTPError`, а он наследует
  `RequestException`. 408, 429 и 5xx остаются неизвестностью — там запрос мог быть
  принят.
- **Подтверждение человека сильнее лимитов.** Ветка «уже подтверждено» в
  `authorize` возвращает `allow`, не переспрашивая политику. Это осознанно: к
  моменту подтверждения операция уже прошла разбор, лимиты попали в текст,
  который человек прочитал, и он решил. Отменять его решение задним числом хуже,
  чем разово выйти за потолок.
- **При недоступном фаерволе по умолчанию отказ** (`TBANK_FIREWALL_FAILMODE=closed`).
  «Фаервол упал» не может означать «значит, можно всё».
- **guard ходит мимо системного прокси** (`ProxyHandler({})`). Без этого `HTTP_PROXY`
  из окружения уводил запрос про перевод денег на чужой хост — так это и нашлось.
- **Сравнение по сумме при отсутствующей сумме не совпадает.** Правило «больше 5000»
  не пропускает вызов без суммы; для этого есть отдельное правило `amount is_empty`,
  и оно в сиде (чекаут без `expected_sum`).

## Тесты

Обе части следуют стилю upstream: **без pytest**, каждый файл — самостоятельный
скрипт, `run_all.py` запускает их в отдельных процессах.

**Апстримовый набор `mcp/tests/` надо гонять с `TBANK_FIREWALL=0`.** Он проверяет
клиент банка, а не политику, и при включённом фаерволе денежные туллы честно
возвращают запрос на подтверждение вместо платежа — четыре теста падают именно
поэтому, а не из-за поломки. Врезку проверяет `tests/test_firewall_guard.py`
против заглушки; настоящий сервис — `firewall/tests/`.

Ещё две ловушки: если в вебморде **скрыть** тул (`hidden`), он не регистрируется, и
`test_docs_match_code.py` с `test_trace.py` начнут ругаться на несуществующий тул —
это ожидаемо для настроенной установки, тесты рассчитаны на политику по умолчанию.
И любой новый тул надо назвать в `TOOL_KINDS`, в каком-нибудь `SKILL.md` и в доке —
`test_docs_match_code.py` требует все три.

## Отношения с upstream

`mcp/` — вендоренная копия с сохранённым `.git`, поэтому `git -C mcp diff` и
`git -C mcp log` показывают ровно наши изменения относительно апстрима
(база: `3d1496a`). Наши правки держатся минимальными и локализованными:

- `src/guard.py` — новый файл, вся логика здесь;
- `src/server.py` — импорт, `_HIDDEN`, `_traced_tool`, три тула `firewall_*`,
  три строки в `TOOL_KINDS`;
- `pyproject.toml` — пин `mcp<2`;
- `README.md`, `skills/tbank/SKILL.md` — документация врезки.

Обновление из апстрима: `git -C mcp pull`, разрешить конфликты в этих файлах.

## Переменные окружения

**MCP:** `TBANK_FIREWALL_URL` (по умолчанию `http://127.0.0.1:8080`),
`TBANK_FIREWALL` (`0` — выключить врезку целиком), `TBANK_FIREWALL_FAILMODE`
(`closed` | `read-open` | `open`), `TBANK_FIREWALL_TIMEOUT`, `TBANK_AGENT_NAME`.
Плюс все переменные апстрима (`TBANK_SESSION`, `TBANK_TRACE`, …) — см. `mcp/README.md`.

**Фаервол:** `TBANK_FW_DB` (путь к SQLite), `TZ` (важно: окна лимитов календарные),
`TBANK_FW_HOST`, `TBANK_FW_PORT`.

**Демон входа:** `TBANK_AUTHD_PORT` (8765), `TBANK_AUTHD_ORIGINS` — список
источников, которым разрешён CORS. Меняете порт вебморды — добавьте её адрес сюда,
иначе браузер завернёт запрос на preflight.

Новые колонки в существующих таблицах добавляются через `db.MIGRATIONS`, а не в
`SCHEMA`: база живёт в volume и переживает пересборку образа, а
`CREATE TABLE IF NOT EXISTS` уже существующую таблицу не трогает.

## Чего ещё нет

- **Аутентификации в вебморде.** Поэтому compose биндит `127.0.0.1:8080`. Прежде чем
  выставлять наружу — нужен вход; это первый пункт, а не «потом».
- Уведомлений (пуш/телега) о том, что операция ждёт подтверждения: человек узнаёт об
  этом от агента или из вебморды.
- Мобильного приложения и голосового входа.
